# v2.0.4 版本更新说明

> **发布日期**：2026年11月27日
> **版本类型**：性能与稳定性优化
> **主题**：索引体积压缩 + 构建稳定性提升

---

## 📋 版本概述

小遥搜索 v2.0.4 针对用户反馈的**索引体积超过源文件**和**索引构建卡死**问题，从向量压缩、全文索引去重、正文存储策略三个方面进行了优化。

在 38 万分块的实测场景中，Faiss 向量索引从 **1.57GB 降至约 392MB（-75%）**；已有索引在应用启动时自动迁移，**无需重新嵌入或重建索引**。

### 核心亮点

- 🗜️ **Faiss 向量量化**：支持 `flat / sq8 / fp16`，默认 SQ8，体积降低约 75%
- 🔄 **启动自动迁移**：已有 Flat 索引后台自动转换，用户无感
- 🧹 **Whoosh 去重**：全文索引不再重复存储正文，新写入体积降低约 50%
- 📄 **正文预览存储**：`file_content` 只保留 2000 字预览，数据库明显瘦身
- 🛡️ **迁移安全**：召回校验 + 原子替换，失败自动保留原索引
- 🤖 **无需重建**：不涉及数据库结构变更，不新增依赖

---

## 🎯 问题背景

| 现象 | 根因 |
|------|------|
| 索引体积比源文件还大 | 同一份正文在 `file_chunks` 和 Whoosh 中各存一份；`file_content` 又存一份完整正文；Faiss 使用 Float32 全精度向量 |
| 向量索引占用过高 | BGE-M3 输出 1024 维，每个分块 Flat 占 4KB，38 万块即 1.57GB |
| 构建到 84% 卡死、前端提示网络失败 | 分块/向量化/写库全部在事件循环中同步执行，阻塞 API；大量 Python float 占用内存 |
| 重复任务互相覆盖 | 同一索引任务被启动两次，第二个任务失败后又把第一个任务标记为失败 |

v2.0.3 已解决构建阻塞、任务并发和进度问题；v2.0.4 继续解决**体积**问题。

## ✨ 新增与优化

### 1. Faiss 向量量化

BGE-M3 输出 1024 维向量，每个分块的存储占用如下：

| 模式 | Faiss 索引类型 | 每块占用 | 38 万块合计 | 召回率 |
|------|---------------|---------|------------|--------|
| `flat` | `IndexFlatIP` | 4KB | 1.57GB | 100% |
| `sq8`（默认） | `IndexScalarQuantizer(QT_8bit)` | 1KB | 392MB | 约 99% |
| `fp16` | `IndexScalarQuantizer(QT_fp16)` | 2KB | 785MB | 接近 100% |

配置方式：

```ini
# 分块向量量化方式: flat（不压缩） / sq8（4 倍压缩，默认） / fp16（2 倍压缩）
CHUNK_FAISS_QUANTIZER=sq8
```

三个模式**全部无条件生效**，没有“分块数少于某个值就退回 Flat”的隐藏阈值。

### 2. 启动自动迁移已有索引

升级后首次启动时，后台线程会自动检查并迁移已有索引：

1. 读取配置与现有索引类型，已是目标类型则跳过（幂等）
2. 校验 `metadata.chunk_ids` 数量与 `index.ntotal` 一致，不一致则跳过
3. 从原索引采样（默认 50000 条）训练量化器
4. 分批重建向量（20000 条/批），日志每 10% 输出一次进度
5. 用 50 条真实向量做 Top-K 召回校验，低于 95% 放弃迁移
6. 写入临时文件，释放 mmap 后原子替换
7. 重新加载搜索服务，完成迁移

**迁移只做向量压缩，不重新调用嵌入模型。**

日志示例：

```text
[索引迁移] 开始检查: 配置=sq8, 索引=.../document_index_chunks.faiss
[索引迁移] 检测到分块向量索引需要量化: flat -> sq8，共 50000 条
[索引迁移] 进度 40% (20000/50000)
[索引迁移] 进度 80% (40000/50000)
[索引迁移] 进度 100% (50000/50000)
[索引迁移] 召回校验: 99.00% (阈值 95%)
[索引迁移] 写入完成: 195MB -> 49MB
[索引迁移] 完成，搜索索引已重新加载
```

### 3. Whoosh 全文索引去重

旧实现中，分块正文同时写入 `file_chunks.content` 和 Whoosh 的 `content_stored` 字段，同一份内容存两次。

新实现保留 schema 字段以兼容旧索引，但**新写入不再填充 `content_stored`**。正文统一从 `file_chunks` 读取，旧索引会在文件重新索引后逐步收敛。

### 4. `file_content` 只存预览

| 字段 | 旧行为 | 新行为 |
|------|--------|--------|
| `file_contents.content` | 完整正文 | 前 2000 字预览 |
| `file_contents.content_length` | 完整正文长度 | 完整正文长度（不变） |

完整正文只保留在 `file_chunks` 中，满足分块检索需要；`file_content` 不再承担全文存储职责。

### 5. 构建稳定性（v2.0.3 延续）

以下能力已在 v2.0.3 发布，本版本继续生效：

- 流式分批构建（4096 块/批），内存峰值降低约 60%
- 索引任务在线程池执行，构建期间 API 正常响应
- SQLite WAL + `busy_timeout`，避免写锁阻塞
- 拒绝重复启动同一索引任务，启动时清理僵尸任务
- 进度实时更新，停止立即生效

## ⚙️ 新增配置项

```ini
# 单次向量推理的批大小（GPU 建议 256；CPU 环境会自动降到 32）
CHUNK_EMBEDDING_BATCH_SIZE=256

# 流式构建时每批处理的分块数（内存紧张时可调低到 2048）
CHUNK_PIPELINE_BATCH_CHUNKS=4096

# 分块向量量化方式: flat / sq8（默认） / fp16
CHUNK_FAISS_QUANTIZER=sq8

# 量化训练采样数量（默认 50000）
CHUNK_FAISS_TRAINING_SAMPLE=50000

# 启动时自动迁移已有分块向量索引（默认 true；迁移失败会保留原索引）
CHUNK_FAISS_MIGRATE_ON_STARTUP=true
```

| 配置项 | 默认值 | 说明 |
|--------|--------|------|
| `CHUNK_EMBEDDING_BATCH_SIZE` | `256` | 单次向量推理批大小；检测到 CPU 时自动降到 32 |
| `CHUNK_PIPELINE_BATCH_CHUNKS` | `4096` | 流式构建每批处理的分块数 |
| `CHUNK_FAISS_QUANTIZER` | `sq8` | 向量量化方式 |
| `CHUNK_FAISS_TRAINING_SAMPLE` | `50000` | 量化训练采样数量，越大越精确、迁移越慢 |
| `CHUNK_FAISS_MIGRATE_ON_STARTUP` | `true` | 启动时自动迁移已有索引 |

## ❓ 常见问题

### Q1: v2.0.4 需要重新构建索引吗？

**A**: 不需要。启动时后台自动把已有 Flat 索引转换为 SQ8，不会重新调用嵌入模型。

### Q2: 迁移失败怎么办？

**A**: 迁移过程使用临时文件 + 原子替换，失败会保留原索引并清理临时文件，不影响搜索。可查看日志中的 `[索引迁移]` 关键字定位原因。

### Q3: SQ8 会影响搜索准确率吗？

**A**: 实测召回率约 99%。迁移前会自动做 Top-K 召回校验，低于 95% 会放弃迁移并保留原索引。

### Q4: 为什么重新索引后体积还能再降？

**A**: 迁移只能压缩向量；Whoosh 去重和 `file_content` 预览只对**新写入**的数据生效。文件重新索引后，旧的重复正文才会被替换。

### Q5: 可以切回 flat 吗？

**A**: 可以配置 `CHUNK_FAISS_QUANTIZER=flat`，但量化索引无法无损还原为 Flat，需要重建索引。日志会给出提示。

### Q6: 迁移需要多久？

**A**: 38 万块约 1-3 分钟，取决于磁盘和 CPU。迁移在后台执行，不阻塞使用。

### Q7: CPU 环境能用吗？

**A**: 可以。CPU 环境下嵌入批大小会自动降到 32，迁移是纯向量计算，同样可用，只是速度较慢。

## 🏗️ 技术决策

### 为什么选择 ScalarQuantizer，而不是 IVF / PQ？

- 分块索引需要支持增量追加，`IndexFlatIP` 和 `IndexScalarQuantizer` 都支持直接 `add`
- IVF 需要维护倒排列表和训练集，增量更新与删除更复杂
- SQ8 实现简单、召回稳定，且压缩率已能满足需求

### 为什么默认 SQ8，而不是 FP16？

- SQ8 压缩 4 倍，FP16 只压缩 2 倍
- SQ8 实测召回约 99%，对搜索场景足够
- 需要更高召回时可切换 FP16，无需改代码

### 为什么迁移而不是重建？

- 重建需要重新调用 BGE-M3 嵌入 38 万块，GPU 上也要数十分钟到数小时
- 迁移只做向量类型转换，几十秒到几分钟即可完成
- 迁移失败可回退，重建失败则可能丢失索引
