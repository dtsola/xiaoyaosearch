## 🧠 v2.0分块处理架构 (新增)

### 分块策略设计
```mermaid
graph LR
    A[原始文件内容] --> B[智能分块处理]
    B --> C{内容长度检查}
    C -->|≤500字符| D[单块处理]
    C -->|>500字符| E[多块智能分块]
    E --> F[重叠处理]
    F --> G[语义边界优化]
    G --> H[批量向量化]
    H --> I[独立索引存储]
    I --> J[透明结果聚合]

    D --> K[传统索引流程]
    J --> L[统一搜索接口]
```

### 分块处理核心逻辑
1. **智能分块判断** - 内容>500字符时自动启用分块
2. **段落边界识别** - 按自然段落分割，保持语义完整
3. **重叠处理** - 50字符重叠，避免边界截断问题
4. **批量向量化** - 所有分块同时生成向量，提高效率
5. **透明聚合** - 搜索时自动选择最佳分块，对外透明

## 🔍 各格式的具体构建逻辑

### 📄 文档类（智能分块支持）

**构建流程：**

```mermaid
graph LR
    A[扫描识别] --> B[内容解析]
    B --> C[文本提取]
    C --> D{长度判断}
    D -->|≤500字符| E[单块处理]
    D -->|>500字符| F[智能分块处理]
    F --> G[向量生成]
    G --> H[索引存储]
    H --> I[数据库记录]

    E --> G
```

1. **扫描识别** - 文件扫描器识别文件扩展名
2. **内容解析** - 内容解析器调用对应解析方法
3. **文本提取** - 提取完整文本内容（最大1MB）
4. **智能分块判断** - v2.0新增：内容长度>500字符时自动分块
5. **分块策略执行** - v2.0新增：500字符+50字符重叠
6. **批量向量生成** - v2.0优化：支持批量处理
7. **索引存储** - 分块独立存储到Faiss和Whoosh
8. **数据库记录** - files表+file_chunks表双重记录

**输出示例：**
```javascript
// v1.0传统模式
{

    content: "完整的文档文本内容",
    has_error: false,

// v2.0分块模式
{
  files: {
```

### 📄 经典Office格式处理说明

**构建流程：**

```mermaid
graph LR
    A[格式识别] --> B[解析器选择]
    B --> C[工具检测]
    C --> D[内容提取]
    D --> E[语言检测]
    E --> F[向量生成]
    F --> G[索引存储]
```

**经典Word文档 (.doc)：**
1. **格式识别** - 通过文件扩展名识别经典Word格式
2. **工具检测** - 优先检测antiword工具是否可用
3. **内容提取** - 使用antiword提取文档文本内容
4. **降级处理** - antiword不可用时降级为元数据提取
5. **语言检测** - 自动检测中英文内容
6. **索引存储** - 生成向量索引和全文索引

**经典Excel (.xls) 和 PowerPoint (.ppt)：**
1. **兼容处理** - 使用现代Office库处理经典格式（有限支持）
2. **内容提取** - 提取表格数据或演示文稿文本
3. **降级提示** - 建议用户转换为现代格式获得更好支持
4. **元数据记录** - 详细记录处理状态和建议

**特殊说明：**
- 经典格式需要额外工具支持（如antiword）
- 处理成功时置信度为0.7-0.8
- 降级处理时置信度为0.3，并提供转换建议
- 所有处理失败都有详细的错误记录

### 🎬 视频类（音频转录 + 关键帧提取 + 元数据）

**构建流程：**

```mermaid
graph LR
    A[扫描识别] --> B[时长检测]
    B --> C[时长控制]
    C --> D[功能开关判断]

    D --> F[关键帧提取]
    E --> G[语音转文字]
    F --> H[CLIP图像理解]
    G --> I[元数据解析]
    H --> I
    I --> J[向量生成]
    J --> K[索引存储]
    K --> L[数据库记录]
```

1. **扫描识别** - 识别视频文件扩展名
2. **时长检测** - 使用FFmpeg获取视频时长和分辨率
3. **时长控制** - 超过最大时长（默认600秒）自动截取
4. **功能开关判断** - 检查是否启用视频帧搜索功能
5. **音频提取** - 使用ffmpeg从视频中提取音频轨道
6. **关键帧提取** - 使用FFmpeg按间隔提取关键帧（默认10秒）
7. **语音转文字** - 使用FasterWhisper模型转录音频为文本
8. **CLIP图像理解** - 使用Chinese-CLIP模型理解视频帧语义
9. **元数据解析** - 提取视频分辨率、帧率、编码等信息
10. **嵌入向量生成** - 音频文本使用BGE-M3，视频帧使用CN-CLIP
11. **索引存储** - 文本向量存Faiss，图像向量存Faiss，全文存Whoosh
12. **数据库记录** - 在 files、file_content 和 video_frames 表创建记录

## 🔄 实时通信架构优化 (v2.2新增)

### WebSocket → HTTP轮询迁移

#### 迁移背景
- **兼容性提升**: HTTP轮询兼容性更好，易于调试和测试
- **架构简化**: 移除WebSocket长连接复杂性，降低系统耦合度
- **性能优化**: 避免长连接资源占用，减少服务器负载
- **前端友好**: 配合防抖和智能轮询，用户体验更佳

#### 新的轮询接口架构
```mermaid
graph LR
    A[前端轮询请求] --> B[实时消息API]
    B --> C[索引进度查询]
    B --> D[搜索建议查询]
    B --> E[活跃任务查询]
    B --> F[轮询配置建议]

    C --> G[数据库查询]
    D --> H[搜索历史分析]
    E --> I[索引任务状态]
    F --> J[配置参数返回]
```

| 接口 | 功能 | 推荐间隔 | 技术特性 |
|------|------|----------|----------|
| **GET /api/realtime/index/{index_id}/progress** | 索引进度实时查询 | 2秒 | 智能完成检测 |
| **GET /api/realtime/search/suggestions** | 搜索建议防抖查询 | 300毫秒 | 配合防抖使用 |

## ⚡ 索引构建性能与体积优化（v2.0.4 新增）

> 解决的问题：大文件索引构建到 84% 卡死、前端提示网络连接失败、服务无响应；索引体积超过源文件（38 万块产生 1.57GB 向量）。

### 1. 流式分批构建

分块索引由「全部文档一次性分块 + 全部向量化 + 全部入库」改为流式分批：

```mermaid
graph LR
    A[按文档批次读取] --> B[分块]
    B --> C[生成雪花ID]
    C --> D[批量向量化 4096块/批]
    D --> E[批量写 file_chunks]
    E --> F[Faiss add]
    F --> G[Whoosh 写入]
    G --> H{还有文档?}
    H -->|是| A
    H -->|否| I[原子落盘 + 重载搜索服务]
```

**关键点**：

- 每批处理完立即释放内存，内存峰值降低约 60%
- 向量以 `float32 ndarray` 在内存中传递，不再生成数亿个 Python float
- 分块正文只写一次（`file_chunks`），Whoosh 不再重复存储
- Faiss / Whoosh 落盘使用临时文件 + `os.replace` 原子替换，构建中断不会损坏旧索引

### 2. 构建期间不阻塞服务

| 问题 | 处理方式 |
|------|----------|
| 同步索引操作跑在 asyncio 事件循环里 | 索引任务改用同步函数 + `asyncio.run`，由 FastAPI `BackgroundTasks` 调度到线程池 |
| SQLite 写锁阻塞其他请求 | 启用 WAL、`synchronous=NORMAL`、`busy_timeout=30000`，连接池改为 `NullPool` |
| 构建期间 API 无响应 | 构建期间搜索、设置、状态查询等 API 正常响应 |

### 3. Faiss 向量量化

BGE-M3 输出 1024 维向量，每个分块占用：

| 模式 | 每块占用 | 38 万块合计 | 召回率 | 说明 |
|------|---------|------------|--------|------|
| `flat` | 4KB | 1.57GB | 100% | 不压缩，全精度 |
| `sq8`（默认） | 1KB | 392MB | 约 99% | 4 倍压缩，推荐 |
| `fp16` | 2KB | 785MB | 接近 100% | 2 倍压缩 |

**启动自动迁移流程**（`CHUNK_FAISS_MIGRATE_ON_STARTUP=true`）：

1. 检查配置与现有索引类型，已是目标类型则跳过（幂等）
2. 校验 `metadata.chunk_ids` 数量与 `index.ntotal` 一致，不一致则跳过
3. 从原索引采样（默认 50000 条）训练量化器
4. 分批重建向量（20000 条/批），每 10% 输出进度日志
5. 用真实向量做 Top-K 召回校验，低于 95% 放弃迁移
6. 写临时文件后原子替换，释放 mmap 后重载搜索服务
7. 任一步失败都保留原索引并清理临时文件

**说明**：迁移只做向量压缩，不重新调用嵌入模型；升级后首次启动自动完成，无需重建索引。

### 4. Whoosh 全文索引去重

- 旧实现同时在 `file_chunks.content` 和 Whoosh 的 `content_stored` 中保存正文，磁盘占用翻倍
- 新实现保留 schema 字段以兼容旧索引，但**新写入不再填充 `content_stored`**
- 正文统一从 `file_chunks` 读取，旧索引在文件重新索引后逐步收敛

### 5. file_content 只存预览

| 字段 | 旧行为 | 新行为 |
|------|--------|--------|
| `file_contents.content` | 完整正文 | 前 2000 字预览 |
| `file_contents.content_length` | 完整正文长度 | 完整正文长度（不变） |

正文完整内容只保留在 `file_chunks` 中，满足分块检索需要；`file_content` 不再承担全文存储职责。

### 6. 索引任务并发保护

- 已存在 `pending` / `processing` 任务时，拒绝重复创建（超过 10 分钟的 `pending` 视为僵尸任务，允许重新创建）
- 服务启动时把残留的 `pending` / `processing` 任务标记为失败（原因：服务重启，任务中断）
- 索引任务支持中途停止：`should_stop` 回调在分块、向量化、写库各阶段检查，停止后返回 `stopped` 状态

### 7. 配置项

```ini
# 单次向量推理的批大小（GPU 建议 256；CPU 环境会自动降到 32）
CHUNK_EMBEDDING_BATCH_SIZE=256

# 流式构建时每批处理的分块数（内存紧张时可调低到 2048）
CHUNK_PIPELINE_BATCH_CHUNKS=4096

# 分块向量量化方式: flat / sq8（默认） / fp16
CHUNK_FAISS_QUANTIZER=sq8

# 量化训练采样数量
CHUNK_FAISS_TRAINING_SAMPLE=50000

# 启动时自动迁移已有分块向量索引
CHUNK_FAISS_MIGRATE_ON_STARTUP=true
```

### 8. 体积收益

| 阶段 | Faiss | Whoosh | SQLite 正文 | 磁盘合计 | UI 索引大小 |
|------|-------|--------|------------|---------|------------|
| 优化前（38 万块） | 1.57GB | ~0.54GB | ~0.55GB | ~2.66GB | ~2.11GB |
| 升级后立即（仅迁移） | 392MB | ~0.54GB | ~0.55GB | ~1.48GB（-44%） | ~0.93GB（-56%） |
| 重新索引后 | 392MB | ~0.28GB | ~0.31GB | ~0.98GB（-63%） | ~0.67GB（-68%） |

通用估算：每个分块约节省 3KB，`节省空间 ≈ 分块数 × 3KB`。

### 9. 兼容性

- 旧 Flat 索引可直接加载、搜索，无需重建
- 配置从 `flat` 切到 `sq8/fp16`：启动时自动迁移；增量更新前也会自动转换
- 配置从 `sq8/fp16` 切回 `flat`：需要重建索引（日志会提示）
- 本次优化不涉及数据库表结构变更，不新增依赖
